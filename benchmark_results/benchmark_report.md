## Method

- Both modes call the same `run_log_pipeline()` on the same file. `workers = 1` runs the
  sequential path; `workers = N > 1` runs the concurrent path (main thread reads,
  N threads parse, 1 thread aggregates in file order).
- Each run is a separate process. Time is measured inside the process around the
  pipeline call only (dataset generation and process start-up are excluded).
- Warm-up runs are discarded and prime the OS file cache. The same file and read
  path are used for each mode; Windows may still evict cached data under pressure.
- Repetitions rotate the configuration order to reduce ordering bias.
- Peak memory: Windows `PeakWorkingSetSize` and `PeakPagefileUsage` (peak commit)
  of the run's process. Baseline working set is measured before the pipeline starts.
- Batch latency: time from a batch being read until its analysis completes.
- Speedup = sequential median / configuration median at the same batch size.
  The verdict is **faster** or **slower** only if the slowest and fastest runs of the two
  configurations do not overlap; otherwise it is **no clear difference**.
- Every run's analysis output is hashed; *Results match* confirms it equals the
  sequential result for the same dataset and batch size.
